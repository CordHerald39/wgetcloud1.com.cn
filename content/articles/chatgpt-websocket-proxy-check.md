能登录 ChatGPT 网页、历史记录也能打开，但发送问题后回答卡住、中途断线或只出现半句，通常不是 Cookie 立刻失效，而是短连接已通、长连接没保住。登录和静态资源走常规 HTTP(S)；对话流式输出依赖持续通道，常见为 WebSocket 升级，也可能是长寿命流式 HTTP。代理或网关只转发了页面、却在 Upgrade、101 切换或空闲超时上失败，就会出现能进门、说不完的症状。

## 先看公开状态再动本机

排查由外到内。多条网络、多台设备同时无法生成回复时，先对照站点公开状态，排除对端故障。本机确认系统时间正确：偏差过大会让 TLS 会话反复失败，页面仍可能打开，后续通道却不稳定。再确认刷新后登录态还在、能进入对话页。这一步适用于所有浏览器用户，不绑定某一客户端或某一条线路。

## 隐身窗口与扩展隔离

使用全新隐身（无痕）窗口打开对话页，不要启用扩展。广告拦截、脚本管理、HTTPS 扫描、流量改写类扩展经常拦截 Upgrade 或改写响应头，登录态仍在，流式数据却被丢掉。若隐身窗口正常、普通窗口异常，在普通窗口中逐个关闭扩展并复测。公司托管浏览器或强制安装的安全套件同样可能检查 WebSocket；个人无法关闭时，记录复现时间与浏览器版本，交给管理员。本机若还运行代理类应用，在 macOS 上应到系统偏好设置的安全性与隐私中查看网络等权限是否已授予，避免应用处于半拦截状态。

## 对照直连、系统代理与分流规则

一次只改变一项。第一，当前浏览器走现有系统代理，发送一条短问题，观察是否完整出字。第二，换一条网络（例如手机热点），尽量不经过同一套代理后再发送。第三，若使用规则分流，检查对话相关域名是否与静态站点被拆到不同出口：一个直连、一个进入代理组，足以造成页面能开、会话中断。

系统代理主要接管遵守系统代理设置的程序；部分进程里的 WebSocket 可能绕过代理或走另一套网络栈。虚拟网卡模式会接管更多流量，但同样取决于内核是否放行升级请求。不要同时开启多套客户端，以免本地 HTTP 端口、SOCKS 端口或混合端口争用；浏览器填写的代理协议必须与实际监听端口一致。这一对照适用于能够切换网络或规则、且故障只出现在流式回复阶段的环境。

## 升级失败与超时交给管理员

个人不要关闭证书校验来强行访问。出现证书告警时，应走正常的证书签发与中间盒策略。管理员侧建议按下列顺序查看日志，而不是先改节点的加密或传输层字段：确认浏览器到本地监听端口的请求是否到达，CONNECT 或 Upgrade 有没有被丢弃；确认代理是否原样转发 Connection: Upgrade 以及 WebSocket 相关请求头，有无被内容过滤改写成普通成功响应；确认出口到目标的 101 切换是否完成，失败时区分握手失败、名称不匹配还是空闲超时；检查防火墙、TLS 解密和 WAF 对长连接的空闲切断时间，对话可能持续数分钟，超时过短会表现为答到一半断开。

若节点自身也使用 WebSocket 传输（配置中的网络类型为 ws，并带有路径和 Host 头），必须区分「代理隧道所用的 WebSocket」和「浏览器访问站点所用的 WebSocket」。修改节点路径解决不了中间设备丢弃站点通道的问题。gRPC、HTTP/2 或普通 TCP 节点与浏览器会话通道没有固定对应关系，不能假定某一种传输层一定能保住回复，也不要因为某条线路的介绍文字提到相关能力，就认定当前出口一定可用。

## 适用条件

上述顺序适用于：能够登录、能够看见历史、新消息发送后中断或空白。不适用于整站无法打开、验证流程卡死，或账号本身被限制使用——那些应先处理访问路径与账号策略。不要混用多个系统代理，不要把节点传输配置当成站点接口去改。把日志交给管理员前，去掉订阅链接与节点敏感信息。
